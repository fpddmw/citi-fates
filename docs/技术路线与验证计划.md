# 技术路线与验证计划

- 日期：2026-09-26。
- 对应：[策划案 v1.0](符文构筑Roguelike_策划案_v1.0.md)。
- 状态：技术假设、架构建议与测试准备文档；没有实现或实测结果。
- 目标：验证本地模型能否自主组织词义关系，并将其落实为可执行、可观察、稳定保存的能力。

## 1. 当前需要证明的能力

当前技术研究围绕以下完整链条展开：理解真实词义及玩家融合意图 → 发现和选择关系 → 构造符文结果或技能行为 → 组织整体演出 → 运行并根据反馈修正 → 保存已确认结果。

关键提升是对未逐项预设组合进行合理的关系构造。相关词联想、完整 JSON、文本新颖或大量不同配色，分别属于局部能力指标。

底层原子化提供表达空间，模型尝试发现有意义的组织方式。引擎没有实现的对象、状态或交互，不能仅凭模型描述进入战斗。预设美术资源可以被重新组织；资源种类固定与完整技能固定是不同条件。

## 2. 两种生成任务与战斗执行

| 阶段 | 输入 | 交付 | 当前定位 |
|---|---|---|---|
| 精灵融合 | 实际投入的符文实例、位阶、稳定词义、可选提示、融合规则 | 参与／返还材料、真实结果词候选、结果能力范围及融合判定 | 用户已明确的交互 |
| 法杖技能构造 | 实际装配的符文、词义、位阶及已确定的装配上下文 | 完整行为方案、演出方案、参数和资源依赖 | 用户认可的核心研究方向 |
| 战斗执行 | 已确认技能与当前真实战斗状态 | 命中、状态变化、事件和对应表现 | 程序执行 |

融合与技能构造需要分别建模，避免用一次“生成技能”替代融合出的独立符文。融合成果需要有可用于后续组合的意义；它首次出现时对应的技能只是具体应用。

法杖构造不调用旧“留空补齐词条”机制。没有玩家装配或规则正式产生的符文，不能作为隐藏输入加到技能中。

融合与构造可由同一个模型分阶段完成。调用次数、缓存位置和同步方式通过测量确定，不预设多模型或多代理平台。

## 3. 建议架构：统一方案，分别执行

### 3.1 基础内容层

建议维护四类资料：

1. 词义目录：真实名称、义项、释义依据、适用范围、典型联系与反例。
2. 能力目录：已实现的对象、事件、状态、关系操作、接口类型和成本。
3. 资源目录：素材及其技术条件、风格、可变参数和受支持的使用方式。
4. 局部示例：已经验证的构造和失败修正；与独立评测集分开。

稳定词义不依赖模型每次重新编写。新词候选需要能在可信词义资料中找到依据，未确认的生成释义不自动升级为下一次构造的权威资料。

关系目录提供语义引导和适用条件，不以预先穷举全部词对为目标。是否加入向量检索，依据结构化检索对中文提示的实际覆盖决定。

### 3.2 方案生成层

模型取得与当前输入相关的词义、能力边界和候选资源，提出短而完整的整体方案。行为与演出在同一方案中相互约束。

方案需要回答：哪些词建立了什么关系；作用对象和状态是什么；何时产生、触发与结束；哪些结构和事件具有实际战斗意义；视觉怎样表现这些过程。

这类短设计说明是交付内容，不要求冗长内部推理。可以先形成结构，再检索原料并补充参数；也可以在预检索后一次完成紧凑方案，质量和端到端等待通过对照选择。

### 3.3 校验、运行与反馈层

程序检查引用、接口类型、单位、上下文、材料所有权、事件可达性、状态生命周期和资源成本，再在受控环境执行。

诊断反馈应指出具体失败位置，例如目标类型不兼容、轨迹记录缺失、表现位置与伤害范围不同、资源不支持指定变形。模型可以有限次修正，不使用无上限自我重试。

格式合法不代表词义正确或整体演出好看。语义检查、视觉检查与实战评价分别记录；人工评价保留独立作用。

### 3.4 保存与执行层

最终确认后保存规则、数值、资源与版本，战斗由程序使用真实状态执行该方案。施放、命中和每帧更新不依赖模型推理。

正在构造的候选不直接改写当前装备或物品。取消、超时或实现失败保留旧状态。规则性融合失败另有明确的游戏判定与消耗政策，具体政策仍待设计。

## 4. 行为系统需要的表达能力

以下为按体验反推的候选能力族，不是全部首版必做清单，也不是玩家面前的分类槽位。

| 能力族 | 可以表达的关系 | 需要明确的条件 |
|---|---|---|
| 对象与选择 | 当前目标、曾命中者、投射物、区域、拥有者 | 类型、有效性、敌我归属、筛选范围 |
| 空间与结构 | 轨迹、连接线、节点、包覆、展开与收拢 | 共享几何数据、碰撞精度、运动规则 |
| 状态与所有权 | 附着、标记、积累、消耗、临时借用 | 来源、持续时间、叠层、回收和权限 |
| 记录与读取 | 保存位置、轨迹或对象信息，再按事件使用 | 信息种类、采样、容量、失效和覆盖方式 |
| 事件与时序 | 施放、接触、延迟、返回、周期、结束 | 因果顺序、上下文、有限触发与取消 |
| 关系与转换 | 连接、转移、反射、条件依赖、转换作用 | 兼容类型、守恒／来源规则、允许的转换 |

首轮从代表性案例选择必要能力，记录它们在未预写组合中的复用程度。反复为单个词对添加独占代码，说明通用关系表达需要继续设计。

【重要边界】首版建议使用受约束的行为图或领域数据语言，不执行任意生成的 C#、Lua、Python 或 shader 源码。有限重复和有限实体产生可以表达复杂关系，同时允许分析资源与事件成本。

行为结构需要特别处理跨技能触发：来源、施法实例、重入、目标数量、深度与终止条件。只检查每个节点的数值上限，仍不足以约束组合放大。

## 5. 建议的交付结构

以下名称为项目建议，不是已经存在的代码接口。

| 结构 | 主要内容 | 权威来源 |
|---|---|---|
| FusionRequest | 投入实例、可选意图、内容版本、当前融合规则 | 游戏真实状态 |
| FusionProposal | 参与／返还集合、结果词候选、语义联系、用途承接 | 模型提议，经规则确认 |
| RuneDefinition / RuneInstance | 稳定义项、来源、位阶、可用范围、实例标识 | 可信目录与正式融合成果 |
| DesignBrief | 完整构想、词义与关系依据、行为和演出的共同目标 | 模型短设计说明 |
| SkillSpec | 对象、状态、几何、事件、关系及参数 | 校验后的执行规则 |
| VisualRecipe | 原料引用、结构生成、遮罩与材质加工、必要烘焙 | 合成器支持的资源与操作 |
| PresentationSpec | 事件绑定、曲线、粒子／线带／声音与可读性反馈 | 与实际规则对应的演出方案 |
| ValidationReport | 失败、修正、参数变化与未满足要求 | 独立校验与测试 |
| CompiledSkill | 最终行为、数值、资源哈希、依赖及版本 | 已确认且可复现的实例 |

建议结构具备稳定 ID、明确单位和版本。参与材料与返还材料应按实例或数量形成无重复、无遗漏的分配；模型不得引用库存之外的符文。

每个输入词应有可追踪的贡献：对应哪些对象、关系、事件或与之相连的表现。该追踪帮助审查，并不自动证明语义恰当。

结构约束可使用 llama.cpp 的语法或部分 JSON Schema 支持；接口说明、约束解码和独立校验需要分别维护。支持范围以锁定版本测试，不能假定所有 schema 特性都自动生效。来源见 [调研依据](调研依据.md) 的 T04。

## 6. 视觉合成与美术生产

### 6.1 整体行为决定视觉组织

火网的节点、连线和收缩过程，可以作为行为与表现共享的数据。碰撞和伤害由规则处理；粒子、材质与声音跟随实际位置和事件。

视觉自由主要发生在轮廓组织、运动结构、时序、材质和关系反馈。单词不直接映射到唯一配色或成品特效；随机换皮也不自动形成有意义差异。

### 6.2 两类玩家端产物【建议】

- 运行时实例：使用既有纹理、材质、几何和粒子能力，生成参数不同、组织方式不同的效果。
- 程序烘焙产物：通过受支持的遮罩、噪声、变换、图层或渲染到纹理，产生可保存的局部纹理和图标。

两者都可以扩展表现，无须每项技能都生成一张新图片。合成器允许的形变、图层和分辨率应与资源规范一致。

### 6.3 原料规范【建议】

资源应登记用途、尺寸、透明通道约定、颜色空间、锚点、平铺条件、可变色范围、适用渲染方式、风格、授权来源和内容哈希。

同样包含“火焰”的完整插画、粒子遮罩和动画序列，其用途不同。检索先筛选技术兼容，再考虑语义与外形。

美术验收同时检查亮暗背景、缩小尺寸、较少装饰、敌我辨识与危险前兆。降低质量等级可以减少装饰与纹理成本，但不能改变已获得技能的行为或遮去必要的玩法反馈。

### 6.4 本地图像模型与工作量【候选】

开发端可以使用图像模型生产纹样、遮罩等候选，再清洗、标注、检查风格与组合适配。FLUX.2 klein 4B 是已讨论候选，官方给出约 13GB 显存配置说明；实际运行峰值、资产可用率与完整生产成本仍需在目标环境测试，见 T06。

语言模型可以规划资源使用并调用受控合成方法；直接生成位图需要图像模型或图形算法。两个任务分别评估。

当前不将玩家端部署图像模型设为基础条件。先研究已有原料及程序合成能否形成整体差异，再判断运行时生成新素材的增益。用户可提供的 4090 容器可以用于候选测试或后续适配，尚未接入。

## 7. 本地模型、引擎与存储候选

### 7.1 模型候选【原始技术文档承接，未选型】

| 候选 | 建议验证用途 | 必须实测的内容 |
|---|---|---|
| Qwen3.5-4B | 词义关系、提示承接、完整结构生成的首个候选 | 中文语义、关系质量、输出长度、端到端成本 |
| Qwen3.5-2B | 较低资源成本对照 | 缩小规模后对复杂关系与约束的影响 |
| Qwen3-1.7B | 纯文本候选对照 | 在相同任务与校验条件下的可用率 |

候选来自用户输入文档及本轮调研，不能把官方通用基准换算为本项目成绩。先固定任务和输出形式，再选达到需求的模型；量化前后分别测质量。

llama.cpp 是本地推理候选，固定模型、模板、量化文件、推理版本及后端。是否使用 CPU、集显或独显，取决于同机游戏负载下的实测。依赖资料见 T03、T04。

优先评估已有模型与结构设计。只有错误类型和合格数据足够明确时才研究 LoRA 等专项适配；训练不是本轮前置条件，也不自动改善推理速度。

### 7.2 引擎与素材执行【未选型】

Godot 与 Unity 是原文候选；第一阶段只需选一条后端验证。原生粒子、材质、几何与渲染到纹理能够承担部分执行，但具体组合能力、导出包加载和性能需实测。

研究原型在编辑器中生成资源，不自动等于发行游戏能够加载任意新资源图。玩家端应使用已打包执行模块及受支持的数据、参数和纹理创建接口。

### 7.3 本地存储【建议】

采用可信内容目录与玩家生成成果分离的结构，SQLite 可作为本地目录、实例与任务记录候选；实际素材保存为受管理的文件。参照 T07。

实例与缓存分别处理：临时结果可以淘汰，存档引用的资源必须保留或具备已验证的重建方式。保存结果包含内容版本、规则版本、素材哈希和模型生成记录；重载实例不重新问模型。

如果装配顺序、位置或主次有游戏意义，就进入缓存键；只有玩法明确无序时才规范化为集合。先前输入文档中的技能缓存建议需适配当前融合与装配两层结构。

## 8. 物品事务、失败与稳定性

【工程建议】构造任务经历接收、规划、校验、生成资源、确认提交等可诊断阶段。每个任务具有唯一标识，重复完成通知不能重复扣除物品或发放成果。

库存、精灵和结果的变化在确定的提交步骤发生。生成过程中不提前销毁输入。规则性失败何时判定、损耗什么，在游戏规则明确后由程序统一处理。

取消、模型异常、资源缺失和程序崩溃应可恢复到确定状态。外部资源文件与数据库引用需协调保存，不假定一次数据库事务自动覆盖文件系统。

已获得技能保留语义、行为与数值；更新模型不能静默重生成旧成果。跨设备像素可能存在差异，规则和关键反馈应保持一致，是否保存烘焙图像取决于表现需求。

## 9. 测试需要的初步准备

以下是后续工作清单，本轮仅形成定义，没有编写游戏测试代码、下载模型或生成资产。

| 准备物 | 最小内容 | 用途 |
|---|---|---|
| 小型词义资料集 | 真实词语、义项来源、允许应用、反例及暂定测试位阶 | 检验词义稳定与提示承接 |
| 融合任务集 | 投入实例、不同用途提示、可接受关系范围与消耗规则 | 检验全部／部分／失败的处理 |
| 关系案例集 | 人工解释、行为依赖和观察点，不限定唯一成品 | 检验原子能力的表达力 |
| 能力目录与协议 | 类型、事件、状态、单位、所有权与资源成本 | 使输出真正可执行与可校验 |
| 最小资源包 | 少量可复用原料、技术元数据和一致风格 | 检验整体组合而非素材数量 |
| 战斗实验场 | 能移动／施放／接触／反馈的实际场景及有限敌人行为 | 观察技能使用差异 |
| 测量记录 | 模型与版本、输入输出、失败、等待、内存及运行轨迹 | 比较质量与成本 |

用户原文提出约 30 个词条、每次 2–4 个、数百资源和数百评测等实验规模。这些均为原始建议，本稿不将其固定为内容数量或当前必需工作量。

## 10. 首轮代表性验证题

所有题目为测试准备示例，没有实际结果；用例细节需与首批执行能力共同确定。

| 题型 | 输入或变化 | 观察重点 |
|---|---|---|
| 意图改变 | 同样材料，分别希望撤退、封锁或追击 | 输出是否在可兑现范围内改变方向 |
| 部分融合 | 材料中存在可承接关系与无关项 | 参与者有依据，返还者明确，无多扣漏还 |
| 不可满足要求 | 低位阶材料提出超出能力范围的愿望 | 如实给出有限结果或规则失败，不虚构实现 |
| 同义改写 | 对同一愿望采用不同自然表达 | 主要意图一致，避免靠特定提示格式获利 |
| 结构变化 | 火焰、编织，进一步涉及收缩 | 几何、作用范围、时序与表现是否联动 |
| 记录关系 | 火焰、记忆，分别涉及轨迹与目标 | 记录内容随组合改变，稳定词义保持 |
| 关系迁移 | 同一关系词与不同对象组合 | 超出单个手写样例后的复用能力 |
| 非固定表象 | 相同语义要求使用不同兼容素材 | 意义及玩法保留，轮廓与材质可变化 |
| 稳定实例 | 保存、加载和多次使用同一结果 | 规则与资源引用稳定，不再次生成 |
| 连锁与中断 | 跨技能触发、取消、超时、重复提交 | 有界执行、正确归属与物品一致性 |

## 11. 对照方法与指标

### 11.1 公平对照【建议】

在相同词义、能力接口、资源、位阶预算和合法性校验下比较：人工参考、具有合理兼容规则的程序生成、模型组织。

人工参考用于说明期望质量，不作为所有组合的唯一正确答案。随机生成可以作为附加基线，但不以故意薄弱的随机抽样替代正常规则系统。

精灵候选排序与完整关系生成分开报告。若某输出由规则回退完成，记录回退，不计为模型完整生成成功。

预留未在训练、提示示例或检索答案中出现过的词语组合。已看过的局部能力示例可以复用，但评测不以重放同一完整配方为主要成绩。

### 11.2 测量维度

- 词义：每个词是否按稳定定义参与，提示中的主要需求是否兑现。
- 执行：能否运行、对象与生命周期是否正确、贡献能否追踪。
- 构造差异：移除名称、配色和纯数值后，关系与实际使用是否仍有区别。
- 演出：形态、时序、触发和结束是否与实际作用一致，战斗是否易于判断。
- 稳定性：材料、实例、取消、更新与资源清理是否保持一致。
- 玩家体验：能否形成预期、理解结果并愿意继续构筑；记录预测、解释和实战行为。
- 成本：首次合格率、修复次数、回退率、人工修正时间，以及每个合格成果的总成本。

模型自评只能作为诊断信息，语义与体验需要独立检查。文本嵌入相似度可辅助分析，但不直接表示机制不同或玩家满意。

### 11.3 性能口径

分别测量模型冷启动、热生成、检索、修正、资源合成／上传、缓存命中与完整等待，并记录输出长度、CPU／GPU使用、内存与游戏运行表现。

独立聊天速度不能代表游戏同机负载。原始技术文档的热生成 P95 不超过 10 秒属于挑战目标，本项目可接受等待及目标设备尚未确定，所有时延目前未测。

当前已知使用 Windows 本地环境；先前环境检查见到约 64GB 内存及集成显卡，该观察不构成性能结论或最低配置。用户可提供单卡 RTX 4090 容器，需在接入后记录实际运行条件。

## 12. 后续验证顺序与结论分级

【推进建议，未启动】先用人工关系案例检查行为和演出表达，再将模型接到相同接口验证完整构造，同时独立测试融合意图映射。准备少量合格资源后进行实战与性能测量，错误类型明确后再考虑训练与扩充内容。

模型、行为执行和演出可以分别暴露问题，验收时需要重新走通完整链路。只通过其中一项不标记为整个核心技术已经成立。

| 结果层级 | 能力含义 | 对策划的影响 |
|---|---|---|
| 完整方向成立 | 对未专门预写组合形成合乎词义、可执行且一致的行为与演出 | 继续完善本地生成式构筑 |
| 关系生成成立、素材生成不足 | 用已有资源可以整体组织，新素材收益有限 | 保留核心方向，优先现有原料与程序合成 |
| 只能合理选择候选 | 提示可以映射到已有合法符文或方案 | 精灵后备版本，明确开放性缩减 |
| 质量成立、目标设备成本不合适 | 较强硬件有效，本地成本未达需求 | 研究紧凑方案、量化、缓存与适配，再由用户决定产品取舍 |
| 关系与行为仍不能可靠对应 | 文字成立而执行脱节，或输出缺乏有用差异 | 返回能力和任务设计，不用更大词库掩盖问题 |

模型可替换，技术选择服从实测与体验。后备版本的采用需要明确记录其能力范围，不静默把受限版本计为完整目标达成。
