本文以“用户明确／认可方向”“设计建议”“说明性示例”“待决／待验证”标记决定的来源与成熟度。方向得到认可，不代表所有示例、参数、工程细节或效果已获确认、已经实现。

## 1. 核心定位与体验目标

### 1.1 作品定位【用户明确】

玩家在 Roguelike 战斗中获得承载真实词义的符文，在法杖中组合成技能；还可以向魔法精灵提供符文及可选提示词，影响融合方向，得到新的符文，再继续构筑和战斗。

所有体验围绕具有稳定定义的词语展开。玩家利用日常语言知识形成判断，在技能的实际行为和演出中看见词语之间的关系，并发现意料之中与意料之外的用途。

成长围绕词条本身及其位阶展开。技能数值在规则内生成，玩家通过符文、融合方向、组合与使用方式推进成长。

### 1.2 希望形成的体验【用户认可方向，待游玩验证】

1. 看见一个词，能够对它的作用形成有根据的猜测。
2. 两个或多个词共同形成一种完整现象，组合改变其中各词的作用方式。
3. 新结果有惊喜，回头理解时能找到稳定词义和组合关系的依据。
4. 玩家把已经理解的结果用于实际战斗，并根据战斗问题继续构筑。
5. 已获得的能力可靠、可练习、可复用；发现与掌控可以积累。

这里的“化学反应”描述词义、行为与表现相互影响的体验目标，不要求所有组合服从现实化学，也不要求完整物理模拟。

### 1.3 当前设计重心【用户明确】

先验证“词语关系／符文融合 → 可执行能力 → 整体演出 → 实际战斗使用”这条核心链路。战斗是能力的使用场域，组装与升级页面承载构筑操作。

本阶段不展开完整职业、关卡、经济、敌人名录、剧情或局外成长系统。也不以独立工作台或纯文字合成为完整游戏体验。镜头、控制方式、单局结构、战斗节奏等尚待设计。

## 2. 基本对象与边界

| 对象 | 当前含义 | 状态 |
|---|---|---|
| 词条 | 现实存在、有稳定定义的词语，是构筑的语义基础 | 用户明确 |
| 符文 | 词条在游戏中的物品载体，可以获得、投入融合并装入法杖 | 用户明确 |
| 位阶 | 词条成长的维度，约束其可支持的能力与技能参数范围 | 用户方向；具体体系待定 |
| 魔法精灵 | 在组装界面承接符文融合，可接收玩家的方向性提示 | 用户明确 |
| 符文融合 | 从投入符文中选择全部或部分进行融合，成功后产出新符文 | 用户明确 |
| 法杖组合 | 使用拥有的符文组织成可施放的技能 | 用户明确 |
| 技能实例 | 一份已经确认、可执行且稳定保存的具体能力 | 用户认可方向 |
| 基础能力与资源库 | 引擎支持的对象、事件、状态、关系操作及美术原料 | 技术方向 |

“融合”和“装配”分别处理符文的产生与技能的形成。新符文应具有可继续参与组合的独立意义，其用途不被首次生成的技能永久耗尽。

## 3. 词语体系

### 3.1 真实词语与稳定定义【用户明确】

全部词条使用现实中存在、具有稳定含义的词语。具体事物、性质、动作和抽象概念均可成为候选，例如火焰、寒冰、时间、神圣、反弹、记忆、借用、编织。

这些是语义范围示例，不是已确认的首发词库。融合结果同样遵守真实词语要求，不采用为了技能命名而临时拼造的词条。

一个词可以具有多个现实义项。游戏需要明确采用的义项与适用边界；同一符文的定义保持一致，模型不能在每次使用时悄悄替换它。

“稳定词义”与“唯一技能配方”分别处理：同一个词在不同组合中可以作用于不同对象、参与不同关系，但都需要承接其定义。

### 3.2 分类的作用【用户提出方向，分类未定】

用户提出过“概念”“特性”等类型，帮助组织技能含义，例如火焰、寒冰、时间与神圣、魔法、反弹。

具体分类数量、必需类别、是否存在主次顺序及如何显示，尚未决定。技术上可以按对象、关系、动作、条件等维度分析作用，但这些分析维度不直接成为玩家必须填写的固定槽位。

分类需要允许一个词影响多个层次。例如记忆可能同时影响目标选择、状态保存和触发时机，不能只被压缩为一个固定附加效果。

### 3.3 词义兑现【用户认可方向】

每个参与技能的符文都应有可解释的贡献。贡献可以落实在作用对象、行为关系、结构、条件、时序或与之对应的可观察表现中。只出现名字、颜色或无关装饰，不能代表核心词义已经得到体现。

“神圣”不固定等于白色、金色或某种图案；“火焰”不固定等于火球或直线运动。对于抽象词，需要设计可承接的游戏关系，词典释义本身不会自动规定伤害、目标或几何形状。

【设计建议】为词条维护词义依据、适用义项、典型联系和反例，帮助生成与审查。它们是解释依据，不是穷举完整技能的唯一答案表。

## 4. 获得符文与理解符文

### 4.1 怪物与掉落【用户明确方向】

符文可以由对应某种理念的小怪掉落。怪物行为提供理解该词以及寻找相关材料的线索。

【说明性示例】使弹丸折返的怪物可能与反弹相关；重复先前行动的怪物可能与重复相关。具体敌人、表现、掉落权重及确定性均未定。

【设计建议】通过可辨识敌人或路线提供定向争取材料的机会，支撑稳定构筑。其稳定程度、随机性和成本需要随局内结构确定。

### 4.2 辨识的状态【待决】

用户曾提出由玩家通过装载结果推断符文含义。这一想法可以与真实词义体系结合，但隐藏比例、确认方式、是否显示文字以及知识是否跨局保留，尚未定案。

当前明确取消的是“留空自动补全”的探索玩法。符文辨识不自动因该取消而被确认或废除，也不作为首轮验证的必备系统。

若保留辨识，掉落来源和使用结果需要提供一致线索。长期学习应形成可靠理解，不依靠符文每局任意改换定义。

## 5. 魔法精灵与定向融合

### 5.1 玩家操作【用户明确的最新方向】

玩家在法杖组装界面提供魔法精灵和一组符文进行融合，可以输入可选提示词，让精灵尽量按某个方向寻找结果。

精灵的具体物品形态、取得方式、是否一次性消耗以及使用次数仍待定；本稿不将其补成固定商店、货币或常驻伙伴系统。

提示词表达用途和偏好，例如适合撤退、封锁通路或应对分散目标。玩家不编辑词语定义，也不直接填写技能代码或分配数值。

### 5.2 结果与材料处理【用户明确；失败代价待定】

| 结果 | 成功时的材料处理 | 当前状态 |
|---|---|---|
| 全部融合 | 投入符文全部参与并消失，产出融合结果 | 已明确 |
| 部分融合 | 实际参与者消失，未参与者返还，产出融合结果 | 已明确 |
| 融合失败 | 未形成可交付结果；精灵及材料损耗需明确规则 | 失败存在已明确，代价未定 |

一次融合产出数量、能否重复投入同词、同名符文的实例差异与数量规则，尚未确定。

【设计建议】显示实际参与者、返还者、结果词义及对提示方向的承接情况。所有消耗以最终确认的事务为依据。生成异常、取消或程序失败不冒充规则性融合失败；异常处理保存原有物品。

### 5.3 提示词的影响范围【用户明确方向，落实方式待验证】

提示影响候选关系、材料选择、结果词条及用途倾向。材料、位阶和已实现能力限定可兑现范围；提示不直接授予玩家未投入的高级能力，也不改变某个词的定义。

“尽量”允许多种合理实现和不完全满足，不等于系统可以忽略主要需求。【设计建议】结果说明清楚表达满足了哪一部分、偏离了哪一部分。玩家是否在付出代价前获知尝试方向，需另行设计。

自由提示入口限定在精灵融合。任意输入新词条、直接修改法杖技能程序或聊天驱动所有战斗行为，均未成为当前设计。

### 5.4 融合的语义依据与成长【用户提出方向】

词义相近、相反、可互相转化，或能够形成综合意义的关系，可成为融合依据。用户希望有机会从这些关系中产生更稀有或更高位阶的词条。

新词必须具有独立、稳定的现实含义。相反不必然升阶，相似也不自动意味着值得融合；具体概率、判定与位阶变化待设计。

【说明性示例】投入火焰、水、反弹，并提示希望干扰追兵时，可以讨论由火焰与水产生蒸汽、返还反弹的方向。实际能否遮挡视线、怎样部署及是否成功，还需规则与引擎支持。该例不确立必成配方或唯一结果。

## 6. 法杖装配与技能形成

### 6.1 装配的作用【用户明确】

符文在法杖中组合形成技能。玩家通过所装符文表达构筑，组装界面负责呈现对应能力并承接调整。

槽位数量、法杖数量、每杖技能数量、装配顺序与空间位置的意义、重组代价和重复符文处理均未定。早期“两项技能”“每次两三个词”等只属于助手示例。

装配过程不恢复“留空自动补词”。系统可以确定技能实现所需的形态、时序等细节，但不能因为存在空槽就暗中加入新的符文或无依据能力。

### 6.2 整体构造【用户认可方向】

完整组合共同决定能力中的对象、关系、空间结构、时序和相互作用。加入或更换符文，可以改变其他符文的作用对象与发生方式，而不只是叠加独立效果。

一组词的合理实现可能不唯一。系统需要选出并保存一份具体、可解释的结果。首次生成策略、重新装回同一组合是否必定复用、跨玩家是否共享配方，仍待确定。

### 6.3 稳定构筑【用户明确目标，机制部分待定】

玩家应能够保留和理解已经获得的能力，不必在每次使用时重新面对随机解释。已确认技能由程序执行，保存后的实例不在读档或再次施放时重新生成。

【设计建议】保存已确认的符文身份、位阶、组合上下文、行为结构、数值及资源依赖。新组合和新的融合机会可以产生变化，已有实例保持稳定。

早期保留喜欢部分的讨论，当前由保有符文、装配重组及已有技能复用承接；旧“锁定自动补全字段”的独立玩法不继续生效。

### 6.4 技能之间的构筑关系【方向，细则待定】

完整体验应允许多个能力形成配合，例如一项能力创造条件，另一项利用该条件。共享状态、触发来源、作用对象与持续时间需要明确，防止组合收益只靠词语名称暗示。

技能数量、是否多法杖、主动与被动能力分工，以及跨技能相互作用的首轮范围，均待定。

## 7. 战斗与局内循环

【当前核心循环】战斗并观察理念 → 获得相关符文 → 在组装／升级页面进行法杖重组或精灵融合 → 确认能力 → 返回战斗应对怪物 → 根据实际效果形成下一次构筑意图。

融合不是每场战斗必经的步骤，出现频率尚未确定。玩家可以继续使用可靠构筑，再在获得材料与机会时改变它。

战斗应让玩家认识技能适用条件。例如空间封锁、目标分散、追击压力和施放时机，可以用来检验行为差异。【设计建议】初步实验场只提供足以区分这些用途的敌人行为，不先扩展完整关卡与奖励体系。

镜头形式、角色移动、瞄准方式、施放节奏、蓝耗机制、战斗间暂停与融合等待方式均未定。自动战斗不能未经讨论替代用户希望的实际技能使用体验。

## 8. 成长、位阶与平衡

### 8.1 成长对象【用户明确】

成长围绕词条本身和词条位阶，而不是让玩家不断给某个技能增加攻击力、攻速或更大特效。玩家通过新词、位阶、词义组合与运用方式扩大构筑空间。

技能仍然需要伤害、频率、消耗、范围等运行参数。用户希望这些参数由模型在规则内给定，玩家不直接分配数值成长点数。程序校验与实际测试负责约束其可用性。

### 8.2 位阶与词义范围【用户想法，公式待定】

用户提出：定义越具体，延展范围可能越小；更高位阶应支持更广或更高层次的词义应用，并约束参与技能的攻击、攻速、消耗等上下限。

本稿保留这一设计意图。抽象程度、稀有度、位阶与实际强度之间的映射尚未成立；不能直接把抽象词设为普遍更强，也不能让提升位阶改写词语定义。

位阶提升如何取得、融合后如何继承、同词不同位阶怎样区别、是否存在同名多枚符文，均待细化。

### 8.3 平衡方式【设计建议，待验证】

以作用范围、触发条件、可靠性、持续时间、目标数量、消耗和事件放大等维度评估整体能力。模型提出参数后，需要结合单技能及跨技能测试审查，不能仅凭单项数值落在区间内判定平衡。

强度约束应当保留词义关系的完整性。若削减资源预算会破坏关键行为，应重新设计或拒绝该方案，而不是静默删除某个符文的作用。

具体强度预算、允许的极端构筑、失败损失、掉落稀缺性和重组成本仍待讨论。预设“培养／共鸣”菜单与机械式进化树没有成为当前方案。

## 9. 整体演出与“化学反应”

### 9.1 表现目标【用户明确】

技能的表现形式需要多样，词语不与单一颜色、轮廓、运动方式或示例技能绑定。固定素材库可以支持不同组织方式，模型需要依据整体含义决定它们怎样共同出现和变化。

【设计建议】同时规划行为与演出，使视觉结构、运动、接触、触发和消失过程对应真实规则。伤害不由装饰粒子偶然碰撞决定，表现也不在实际范围之外误导玩家。

少量敌我标识、危险范围、触发前兆等视觉约定有助于战斗理解，不要求每个词独占一种颜色。风格、色彩与材质可以在整体方案内变化。

### 9.2 可检验的差异【设计建议】

判断组合是否改变以下至少一项重要关系，并观察该变化是否影响使用方式：

- 作用于谁或什么：敌人、投射物、既有状态、位置、轨迹等。
- 怎样形成：连续区域、连接线、包覆层、离散节点及其结构变化。
- 怎样发生：先后、延迟、条件、周期和结束方式。
- 怎样相互影响：提供条件、改变去向、消耗状态、转移或转换作用。
- 怎样被看见：与真实事件同步的轮廓、运动、材质和声音反馈。

这些是评价维度，不是强制每项技能同时包含全部维度。名称、颜色和纯数值差异单独记录，不计为关系创新。

### 9.3 说明性案例：火焰与编织【未实现，非固定配方】

火线从不同方向伸出，交错成网；线的位置具有灼烧作用，空隙允许穿过，接触触发对应反馈。编织方向、疏密与展开过程共同改变覆盖和通行路径。

加入收缩后，可以让网线逐渐收拢，危险区域随几何结构移动。玩家根据敌人位置和收拢时机使用它。实际实现可选择足够表达该关系的几何与碰撞方案，不默认完整绳网物理。

编织还可能用于绳索、包覆结构或帘幕。这个例子只帮助检查结构与作用是否一致，不把词绑定为一张网。

### 9.4 说明性案例：火焰、记忆与轨迹【未实现，非固定配方】

保存上次施放路线，在后续规定事件发生时沿路线重新燃烧。视觉提示已记录的位置，真实作用读取同一份记录。

如果组合改为涉及目标，则可研究保存对象信息的另一种实现。玩家改变符文组合，记忆的定义保持稳定；不能将此例误写为允许玩家编辑词义。

### 9.5 说明性案例：火焰与吞噬【未实现，非固定配方】

对规则允许吞噬的敌方弹丸，火焰可以包拢、消解并短暂延续。光带、火星、烟雾分别承担对应阶段的表现职责。

可吞噬对象、资源来源和延续上限必须由方案说明。该例不授予吞噬任意敌人、无限吸收或无条件增长的能力。

## 10. 模型在本作中的作用

### 10.1 核心技术假设【用户认可，待验证】

模型理解词语及玩家意图，发现可成立的联系，选择关系并组织可执行行为，再使用已有美术资源形成一致演出，并根据运行反馈修正。

其价值需要体现在没有逐项预写过的组合上，不能只看相关词联想、文字质量、选择已有特效或数据格式正确。

“自主”指在已提供的词义、材料、位阶、接口和资源条件内形成方案，不意味着自行改写底层能力、修改词义、无限循环自我探索或自行训练。

### 10.2 分工【用户认可方向；协议细节为技术建议】

- 玩家：获取和选择符文，表达融合方向，装配与使用技能。
- 模型：语义理解、关系发现、候选构造、行为与演出组织、受限参数提议。
- 程序：真实状态、物品事务、合法性检查、行为执行、资源生成与加载、保存与复现。
- 开发者：建立可表达关系的基础能力、词义依据与美术规范，评价玩法和生成质量。

模型不必在每次施放或每帧工作。已确认的结果由程序按当前战斗状态执行。融合与首次技能构造是否采用同一模型、分几次调用，仍待测试。

### 10.3 技术路线与后备范围【用户认可继续调研】

优先研究本地模型能否完成头脑风暴、落实方案与组织资源。能够补充新素材时评估其价值和成本；使用预设素材的整体组合能力同样属于核心目标。

若完整生成能力不足，可以保留根据玩家需求映射到已有合法符文候选的精灵功能。这是范围较小的后备版本，不能在评估中将它视为完整语义构造目标已经实现。

仅在开发期用模型预生成内容，也是讨论过的技术对照。当前认可的研究方向继续包含运行时关系构造，不将此前的离线基线建议误记为已经取消本地模型。

## 11. 验证范围与当前工作状态

详细验证口径见 [技术路线与验证计划](技术路线与验证计划.md)。目前没有运行结果，以下是后续准备方向：

1. 同一批材料配不同提示，验证融合方向、参与材料和实际结果是否合理改变。
2. 词义、位阶和材料约束保持一致，检验生成方案是否兑现提示而没有凭空增加能力。
3. 用相同底层能力与素材比较人工参考、规则组合及模型组织，检验实际行为和整体演出的差异。
4. 使用未作为训练／检索答案出现过的组合，观察能否形成可理解关系。
5. 在有实际怪物、命中与反馈的实验场中测试，再测本地延迟、资源开销和存档复现。

本轮文档提供测试准备清单和案例类型，不宣称完成上述测试，也不自动启动原型。单卡 RTX 4090 容器由用户表示可提供，尚未接入；优先在现有本地环境测试可行部分。
